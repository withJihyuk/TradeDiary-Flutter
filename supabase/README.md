# 일기 저장 서버 변경

이 디렉터리는 DB 마이그레이션과 `delete-user` Edge Function의 소스다. 앱의 새 저장 경로는 이 서버 변경과 이미지 Worker 확장을 먼저 배포해야 동작한다.

## 적용 순서

1. 운영과 같은 스키마의 별도 환경에서 마이그레이션을 검증한다. 운영 DB 백업을 확보하고 대상 프로젝트를 확인한다.
2. `migrations/202609050001_diary_durability.sql`을 마이그레이션 이력에 등록하여 한 번 적용한다. 기존 Supabase 프로젝트를 새로 초기화하거나 public 스키마를 재생성하지 않는다.
3. `delete-user` 함수를 배포한다. 기존 GET과 새 POST를 함께 지원한다. 인증 계정 삭제 실패는 비성공 응답이다.
4. 별도 `withJihyuk/supabase_upload_image` 저장소의 `imageIds` 지원 Worker를 배포한다. 기존 API/CDN/R2 키 구조는 유지한다.
5. 검증 계정으로 신규 앱을 확인한 뒤 기존 스토어 릴리즈 절차를 따른다.

2026-09-05 운영 DB에 `202609050001` 마이그레이션을 적용하고 이력을 등록했다. 적용 전 일기·프로필을 저장소 밖의 권한 0600 백업으로 보관했고, 적용 후 일기 610건·프로필 277건 유지와 사용자 범위의 조회를 확인했다. `delete-user`와 이미지 Worker도 배포했다. 스토어 제출은 실행하지 않았다.

## 데이터 계약

- `save_draft(p_id, p_revision, p_mutation_id, p_subject, p_content, p_emotion)`
- `finalize_diary`: 같은 인자. 내용 저장, 한국 날짜 결정, 완료, EXP +1을 한 트랜잭션에서 수행한다.
- `delete_draft(p_id, p_revision, p_mutation_id)`
- 응답: `{status, diary?}`. status는 `saved`, `completed`, `conflict`, `deleted`, `duplicate_day`다. 완료 응답의 `lastMutationId`가 요청과 다르면 다른 기기의 완료이므로 미반영 로컬 내용을 보존한다.
- 운영 DB에서 허용되지 않는 사용자 정의 세션 설정을 사용하지 않는다. 구버전 직접 수정은 이전 재시도 토큰을 지우고, 클라이언트의 토큰 컬럼 직접 쓰기는 차단한다.
- 신규 초안은 revision 0으로 요청한다. 저장 결과의 revision을 다음 요청에 사용한다. 완료 요청은 저장 요청과 다른 UUID를 사용하며, 각 요청의 재시도에는 같은 UUID와 내용을 사용한다. 완료 요청 UUID도 기기에 보존한다.
- `search_diaries(p_query, p_offset, p_limit)`: 완료글만 반환하며 제목과 Delta 텍스트에서 대소문자를 구분하지 않는 문자 그대로의 포함 검색을 수행한다. `%`, `_`, 쉼표를 쿼리 문법으로 해석하지 않는다.
- `diaryDate`는 한국 달력의 `YYYY-MM-DD`이고 `completedAt`은 서버 완료 시각이다. 예전 글은 생성 시각으로 날짜만 채우며 실제 완료 시각은 추측하지 않는다.
- 기존 중복 날짜는 그대로 보존한다. 새 완료는 사용자별 트랜잭션 잠금과 기존 기록 조회, 신규 기록 부분 유니크 인덱스로 하루 한 편을 강제한다.
- EXP는 과거 기록에 소급 지급하지 않는다. 앱이 프로필 EXP를 직접 수정하지 않는다.
- 인증 계정 FK는 `NOT VALID`로 기존 고아 데이터를 보존한다. 새 참조와 이후 계정 삭제에는 FK가 적용된다. 기존 고아 데이터 정리와 FK의 전체 검증은 별도 작업이다.

## 검증과 남은 기기 확인

로컬 SQL에서 저장 재시도, revision 충돌, 완료 재시도/EXP 1회 지급, 한국 날짜, 같은 날짜 신규 중복 거절, 기존 중복 보존, 계정 격리, 로컬 이미지 경로 거절, UTF-16 500자 제한, 문자 그대로의 검색, 계정 삭제 cascade를 확인했다. 검증 과정에 실제 사용자 데이터를 사용하지 않았다. 인증 사용자 권한으로 RPC 실행과 구버전 직접 수정 이후 재시도 토큰 격리도 확인했다.

앱 정적 분석, 기존 모델 테스트, Android 디버그 빌드, iOS 시뮬레이터 빌드가 통과했다. 이 기기에는 지정된 Xcode 26.3이 없어 설치된 Xcode 26.6으로 빌드했다. iOS 시뮬레이터에서 로그인 화면을 확인했다. 임시저장 목록과 빈 화면은 실제 위젯에 예시 데이터를 넣어 별도로 확인했다. 위젯 링크는 시스템의 앱 열기 확인창까지 확인했으며, 실제 콜드·웜 진입과 로그인 후 작성 화면 연결은 아래 기기 검증에 포함한다.

스토어 배포 전 검증 계정과 실제 기기에서 다음 흐름을 확인한다.

- 오프라인 제목·본문·사진 작성 → 기기 저장 표시 확인 → 앱 강제 종료 → 같은 계정으로 복원 → 연결 후 동기화.
- 두 기기에서 같은 초안 수정/삭제/완료 → 미반영 글 보존 및 사본에서 계속 작성.
- 느린 저장 중 추가 입력, 감정 선택 후 뒤로 가기, 완료 응답 유실 후 재시도.
- 계정 전환 직전 시작한 목록·프로필 요청, 로그아웃 후 위젯, 위젯에서 로그인 및 작성 진입.
- 한국 자정 경계, 다른 기기 시간대, 최대 레벨, 긴 닉네임, 큰 글씨와 작은 화면.
- 알림 최초 허용/거부/예약 오류, 탈퇴 서버 오류 및 성공 후 로컬 정리.

## 로컬 보존과 운영상 경계

초안은 앱 지원 디렉터리의 `drafts/<userId>/drafts.json`에 저장된다. 파일 교체는 직렬화되며 사진은 같은 사용자 폴더에 고정 UUID로 보관한다. 로그아웃 시 보존하고 탈퇴 시 삭제한다. 미참조 로컬 사진은 다음 시작 시 정리한다. 앱 삭제나 OS의 앱 데이터 삭제까지 복구하는 장치는 아니다.

이번 변경은 서버 이미지 자동 삭제나 R2 저장소 이전을 포함하지 않는다. 기존 R2 파일에는 소유자 메타데이터가 없으므로 추측으로 삭제하지 않는다. 새 Worker는 소유자·해시를 기록하지만 미참조 파일 수집기는 만들지 않는다.

롤백 시 새 앱 배포를 멈추고 추가 스키마와 로컬 보존 파일을 유지한다. 새 컬럼 삭제나 기존 데이터 복원으로 사용자 작성 내용을 지우는 역마이그레이션은 실행하지 않는다.
